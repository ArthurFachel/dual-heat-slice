# Low-Rank Adapter Initialization via Gradient Surgery for Continual Learning

Official implementation accompanying the paper ["Low-Rank Adapters Initialization via Gradient Surgery for Continual Learning"](https://arxiv.org/abs/2605.12752).

This repository contains:

- SLICE gradient-surgery initialization
- Vanilla LoRA, LoRA-GA, and LoRAM initialization baselines
- Vanilla, O-LoRA, and Dual-Heat continual-learning methods
- An experimental full-fine-tuning pipeline with `dual_heat_full`
- Super-NI, TRACE, and NI-Seq-Opposite task sequences
- Training, standalone evaluation, metric recomputation, and analysis tools

## Correctness and result provenance

The code was audited after the original experiments. The audit found correctness defects in the former Dual-Heat, full-fine-tuning, GradVac, cache, data, evaluation, and metric paths. The current code includes focused repairs and CPU regression tests for those findings.

Important consequences:

- Dual-Heat, `dual_heat_full`, GradVac, full-fine-tuning, and affected evaluation results produced before the repairs must be rerun before being used in a paper or method comparison.
- Existing result files are historical artifacts. Their presence in a checkout does not prove that they were generated by the corrected implementation.
- The headline table near the end of this README reports historical paper results. It is not a post-audit rerun.
- GPU-scale experiments have not been fully revalidated by the regression suite. Run a small experiment on your target hardware before starting a large sweep.

The supported runnable CL methods are:

- LoRA pipeline: `vanilla`, `o_lora`, `dual_heat`
- Full-fine-tuning pipeline: `vanilla`, `dual_heat_full`

SAPT and InfLoRA are not implemented in this checkout. Their legacy launchers are quarantined and exit instead of starting mislabeled experiments.

## Requirements

The intended environment is Python 3.12 with a CUDA 12.6 PyTorch build. Install with:

```bash
pip install -r requirements.txt
```

A minimal Conda wrapper is also provided:

```bash
conda env create -f environment.yml
conda activate cl-lora
```

The PyTorch wheel index is configured in `requirements.txt`. Confirm that its CUDA build is compatible with your NVIDIA driver before training.

### Precision policy

- Pascal GPUs such as GTX 1080 Ti and Titan Xp do not support native bf16. Use fp16.
- Full fine-tuning loads fp32 model weights and lets Hugging Face Trainer manage fp16 autocast and gradient scaling.
- Do not combine an fp16-loaded full model with Trainer `fp16=True`.
- `device_map="auto"` is not used for Trainer-managed training. Use an explicit Accelerate or DDP launch for multi-GPU training.
- Pass `--use-bf16` to the full orchestrator only on hardware with bf16 support.

## Data and supervision

Super-NI instances are formatted as instruction prompts followed by an assistant completion.

Training uses completion-only loss:

- Prompt and padding tokens receive label `-100`.
- Loss is computed only on assistant completion tokens.
- Evaluation preserves every valid Super-NI reference and scores a prediction against the best matching reference.
- A dataset with fewer than two records is rejected instead of duplicating one record into both train and evaluation splits.

TRACE requires a local dataset copy. Configure its path through the project’s task and dataset settings before launching TRACE experiments.

## Quick start

### LoRA smoke run

Use a small sequence and reduced evaluation budgets first:

```bash
CUDA_VISIBLE_DEVICES=0 python -m cl_lora.orchestrator \
  --sequence NI-Seq-Dummy \
  --general-eval-set core \
  --eval-size 10 \
  --task-eval-samples 5 \
  --task-eval-max-new-tokens 32 \
  --run-name smoke_test
```

Runtime depends on the model, hardware, network, and whether model files are already cached.

### SLICE run

```bash
CUDA_VISIBLE_DEVICES=0 python -m cl_lora.orchestrator \
  --sequence NI-Seq-Opposite-v2 \
  --run-name slice_pcgrad_oppv2 \
  --rank 64 \
  --lora-alpha 2 \
  --slice-init \
  --slice-init-method slice \
  --slice-cache-dir slice_cache \
  --slice-max-steps 8 \
  --slice-grad-project \
  --slice-grad-projection-mode global \
  --slice-retain-batch-size-set each_task \
  --slice-projection-method pcgrad
```

Available projection methods:

- `pcgrad`
- `pcgrad_c`
- `gradvac`
- `nullspace`
- `magnitude_preserving`

PCGrad-c example:

```bash
python -m cl_lora.orchestrator \
  --sequence NI-Seq-G2 \
  --run-name slice_pcgrad_c050 \
  --slice-init \
  --slice-grad-project \
  --slice-projection-method pcgrad_c \
  --slice-pcgrad-c 0.50
```

GradVac keeps its target-cosine EMA across stages and stores it in partial resume state.

## Initialization methods

### Vanilla LoRA

Drop `--slice-init` entirely:

```bash
python -m cl_lora.orchestrator \
  --sequence NI-Seq-G2 \
  --run-name vanilla \
  --rank 64 \
  --lora-alpha 2
```

### LoRA-GA

```bash
python -m cl_lora.orchestrator \
  --sequence NI-Seq-G2 \
  --run-name lora_ga \
  --rank 64 \
  --lora-alpha 2 \
  --slice-init \
  --slice-init-method lora_ga \
  --slice-svd-selection lora_ga
```

LoRA-GA requires two disjoint rank-`r` singular-vector slices for each target weight:

```text
2 * rank <= min(weight.shape)
```

Unsupported ranks fail before decomposition. The randomized-SVD product `BA` is approximately zero at initialization, not mathematically exact. Absorption compensates for the residual when enabled.

### LoRAM

```bash
python -m cl_lora.orchestrator \
  --sequence NI-Seq-G2 \
  --run-name loram \
  --rank 64 \
  --lora-alpha 2 \
  --slice-init \
  --slice-init-method loram
```

### Initialization application

SLICE initialization is all-or-nothing by default. Training fails if a computed target cannot be matched to exactly one adapter module. It does not silently continue with a partial initialization.

## SLICE cache

Computed A/B initialization tensors are persisted under the configured cache directory. A second identical call can reuse them without repeating gradient collection and decomposition.

Cache identity includes:

- Model repository or local model identity
- Source revision when available
- A fingerprint of the model’s current live weights
- Prompt-format version
- Current and retain task fingerprints
- Rank and effective LoRA alpha
- Projection and decomposition settings

Including the live-weight fingerprint prevents a fine-tuned or merged model from reusing an initialization computed for an earlier model state.

Delete a cache entry if you change behavior not represented in the cache payload.

## Continual-learning methods

### Vanilla

`vanilla` trains and merges one adapter per task without an additional CL regularizer.

### O-LoRA

O-LoRA penalizes overlap between the current LoRA A matrix and prior-task A matrices:

```bash
python -m cl_lora.orchestrator \
  --sequence NI-Seq-G2 \
  --run-name o_lora \
  --cl-method o_lora \
  --cl-o-lora-lambda 0.5
```

### Dual-Heat for LoRA

Dual-Heat combines:

1. Fast heat, an EMA of post-inhibition output magnitudes with active decay.
2. Optional lateral inhibition based on the heat of other output neurons.
3. Slow heat, a capped incremental mean used for per-neuron EWC scaling.

The LoRA implementation wraps PEFT’s native forward instead of copying PEFT internals. This preserves PEFT adapter selection, `ModuleDict` behavior, dtype conversion, merged or disabled adapters, and adapter variants.

The EWC hook is attached to the combined PEFT module output. Because the base branch is frozen, the resulting per-output-neuron scale reaches both LoRA A and B through the chain rule.

Heat state:

- Is stored in fp32 per device
- Is shared across activation and gradient dtypes
- Is preserved between uninterrupted stages
- Is saved and restored for resumed runs

Usage:

```bash
python -m cl_lora.orchestrator \
  --sequence NI-Seq-G2 \
  --run-name dual_heat \
  --cl-method dual_heat
```

With SLICE:

```bash
python -m cl_lora.orchestrator \
  --sequence NI-Seq-G2 \
  --run-name slice_dual_heat \
  --slice-init \
  --slice-init-method slice \
  --cl-method dual_heat
```

Key parameters:

| Parameter | Flag | Default |
|---|---|---:|
| Fast heat EMA decay | `--cl-dh-fast-decay` | 0.93 |
| Lateral inhibition strength | `--cl-dh-fast-strength` | 2.0 |
| Active fast-heat decay | `--cl-dh-fast-decay-rate` | 0.04 |
| Slow-heat EWC strength | `--cl-dh-slow-strength` | 2.0 |
| Slow-heat memory window | `--cl-dh-slow-window` | unlimited |
| Disable lateral inhibition | `--cl-dh-no-lateral-inhibition` | off |

A Dual-Heat run fails immediately if no compatible LoRA modules are found.

## Experimental full fine-tuning

The full pipeline trains base-model weights directly and does not use PEFT:

```bash
CUDA_VISIBLE_DEVICES=0 python -m cl_lora.orchestrator_full \
  --sequence NI-Seq-G2 \
  --run-name vanilla_full \
  --method vanilla \
  --batch-size 2 \
  --grad-accum 8 \
  --lr 5e-5 \
  --epochs 3
```

Full Dual-Heat:

```bash
CUDA_VISIBLE_DEVICES=0 python -m cl_lora.orchestrator_full \
  --sequence NI-Seq-G2 \
  --run-name dual_heat_full \
  --method dual_heat_full \
  --batch-size 2 \
  --grad-accum 8 \
  --slow-strength 1.5
```

The full orchestrator records effective learning rate, epochs, batch size, gradient accumulation, sequence length, warmup, and precision in `run_config.json`.

General-evaluation strategies are:

- `every_stage`
- `first_and_last`
- `final_only`

Architecture support is intentionally strict. `dual_heat_full` protects matched `nn.Linear` modules and fails when zero target modules are found. GPT-2-style `Conv1D` projections are not silently treated as supported. Validate target coverage before a large run.

## Evaluation

The orchestrators evaluate held-out seen tasks after each stage. General evaluation reports:

- GP: zero-shot general performance
- IP: few-shot in-context performance

For separate training and evaluation:

```bash
CUDA_VISIBLE_DEVICES=0 python -m cl_lora.orchestrator \
  --sequence NI-Seq-G2 \
  --run-name slice_g2 \
  --slice-init \
  --train-only \
  --keep-all-checkpoints

CUDA_VISIBLE_DEVICES=0 python -m cl_lora.eval_standalone run \
  --run-dir results/NI-Seq-G2/slice_g2 \
  --task-eval-samples 64
```

Standalone evaluation reconstructs stage `k` from the base model and adapters `1..k`. SLICE runs retain initialization-correction data needed to replay absorption.

Batch evaluation uses `RUNS_ROOT`, not a positional run-directory argument:

```bash
GPU=0 RUNS_ROOT=results/NI-Seq-G2 bash scripts/eval.sh
```

Use the standalone Python command for one exact run directory.

## Metrics and artifact schema

Every canonical stage record uses:

```json
{
  "stage": 1,
  "trained_task": "task_name",
  "train_report": {},
  "seen_tasks": {},
  "general": {}
}
```

The main artifacts are:

- `run_config.json`: resolved run configuration and environment metadata
- `run_summary.json`: task order, stage records, and final summary
- `results_matrix.json`: score matrix `R[i, j]`
- `metrics.json`: aggregate `AP`, `FP`, `Forget`, `GP`, and `IP`

Definitions:

- AP: mean diagonal performance, `mean(R[i, i])`
- FP: mean final-row performance over available task scores
- Forget: mean of paired per-task differences `R[j, j] - R[T, j]`
- GP: final general zero-shot score
- IP: final general few-shot score

Forget is computed from paired task values. It is not the difference between two means formed from different task sets.

Recompute metrics from stage records with:

```bash
python recompute_metrics.py
```

Legacy Qwen metric names are normalized by the analysis loader, while new Qwen runs write canonical `AP`, `FP`, and `Forget` keys.

## Reproducibility

For an auditable run:

1. Record the Git commit.
2. Use a unique run name.
3. Preserve `run_config.json` and `run_summary.json`.
4. Preserve model and dataset revisions.
5. Keep the same seed, task order, precision, and evaluation budgets.
6. Do not mix historical pre-audit outputs with corrected reruns.
7. Report all seeds and ranks instead of deduplicating them by method name.

The analysis loader treats sequence, method, seed, rank, and source root as part of run identity. Distinct configurations are not silently collapsed into one row.

Focused CPU regression tests cover:

- Finite first and subsequent Dual-Heat updates
- Canonical fp32 heat state across mixed dtypes
- Uninterrupted and resumed state equivalence
- Native PEFT forward compatibility
- Full-orchestrator schema and CLI propagation
- Completion-only label masking
- Multi-reference evaluation
- Paired forgetting
- Task registry and NI488 mapping
- LoRA-GA rank validation
- GradVac gating and persistence

Defined in `cl_lora/task_sequences.py`:

## Historical paper results

The repository may contain tables or output artifacts from the original experiments. Treat them as historical until their provenance is checked against the audit.

In particular, do not present old Dual-Heat, `dual_heat_full`, GradVac, full-fine-tuning, multi-reference evaluation, NI488, or affected metric outputs as corrected results. Rerun those experiments from clean output directories with the current code.

The paper remains the source for its originally reported tables. A corrected post-audit table should include:

- Current Git commit
- Model and dataset revisions
- Precision and hardware
- Rank, alpha, seed, and full resolved configuration
- Number of completed stages and rejected runs
- Mean, standard deviation, and seed count when aggregating
